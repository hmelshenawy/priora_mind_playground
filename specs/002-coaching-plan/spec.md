Feature Specification: Personalized Coaching Plan

Feature Branch: 002-coaching-plan
Feature Directory: specs/002-coaching-plan

Created: 2026-08-01

Status: Draft — Ready for Planning. AI-personalized plan generation is a **core product capability** of this feature (hybrid deterministic + LLM). Launch gates remain: clinical/safety approval of the bilingual CoachingActionLibrary content, legal/privacy approval of the coaching-scope disclaimer, review of the versioned prompt templates (Constitution III), and review of the configured LLM provider's data-retention/training policy (Constitution VI) — see §16.

Input: After a user registers, verifies email, consents, completes the minimum profile, and completes the initial assessment, generate a **personalized, AI-synthesized coaching plan** from the persisted assessment result and profile, and present it on the dashboard in place of the current "Onboarding complete — coaching plan comes in a future release." placeholder. Generation is a **hybrid of deterministic rules and an LLM**: deterministic rules supply the assessment evidence, the approved versioned grounding (library + disclaimer), and the generation instructions, and validate the LLM's structured output; the LLM synthesizes a genuinely personalized, bilingual, non-clinical plan grounded by that bundle. The plan is owned by the user, persisted, progress-trackable, and fully localized in Arabic and English.

## 1. Feature Overview

Priora Mind is an AI-powered mental-wellness and personal growth coaching platform, not a medical, psychiatric, psychological, diagnostic, or emergency service. Feature 001 delivered the first-time user journey through onboarding, assessment, and a non-diagnostic assessment result, ending at a transition point. This feature (002) replaces the dashboard placeholder with the personalized Coaching Plan experience that the transition point pointed to.

The coaching plan is generated from the user's persisted profile and the non-diagnostic Assessment Result produced in feature 001 (eight domain scores and coaching bands, a strongest domain, a support domain, and the user's separately captured priorities). Plan generation in this feature is a **hybrid deterministic + LLM pipeline** and is a **core product capability**:

- **Deterministic side (authoritative)**: eligibility, ownership, assessment-completion, SAFETY_HOLD routing, lifecycle, idempotency, concurrency, safety boundaries, focus-area evidence computation, grounding-bundle assembly, structured-output validation, and version pinning are deterministic domain rules owned by the Coaching module. The LLM **MUST NOT** determine whether a user is eligible or safe to receive a normal plan.
- **LLM side (synthesis)**: an LLM, accessed through an app-owned provider port, synthesizes a genuinely personalized bilingual plan (title, summary, focus areas, goals, actions, per-focus-area reasons) as a strict versioned structured schema, grounded by the supplied bundle. The LLM **MUST NOT** invent diagnoses, clinical conclusions, medication advice, crisis counselling, or unsupported user facts.
- **Grounding + validation**: the approved, versioned CoachingActionLibrary and CoachingDisclaimer are grounding sources that bound and constrain the LLM output (the library grounds and constrains the allowed goal/action identifiers — it is not a pick-list); a deterministic validator rejects invalid or unsafe output before persistence, so no unusable plan is ever stored.

The plan is created once per user (idempotent generation start) and pinned to the assessment version and result that produced it. Generation is asynchronous and tracks **two independent concepts**: a **GenerationStatus** (`PENDING → GENERATING → READY`, or `→ FAILED`) for one generation attempt, and a **PlanStatus** (`PROPOSED | ACTIVE | COMPLETED`) for the plan's lifecycle. A plan has no usable lifecycle/content until `generationStatus = READY`; successful validated generation transitions `generationStatus → READY` and `planStatus → PROPOSED` **atomically**. Because the plan is AI-generated, the Constitution requires **explicit user acceptance before activation** (Constitution IV): a `PROPOSED` plan becomes `ACTIVE` only when the user accepts it (`POST /coaching/plan/accept`); action tracking is enabled only when `generationStatus = READY` and the plan is `ACTIVE` or `COMPLETED`. Users can then mark action steps complete or incomplete; progress persists across reloads and login sessions, and the plan auto-transitions `ACTIVE ⇄ COMPLETED` based on action progress (this lifecycle transition touches only `planStatus`). The backend remains authoritative for eligibility, ownership, and routing: only authenticated users whose onboarding is `COMPLETED` and who are not in `SAFETY_HOLD` receive a plan. SAFETY_HOLD users remain in the existing safety flow and never enter plan generation.

This feature is bounded to the plan itself: it does not add AI-coach chat, coaching sessions, streaming responses, conversation memory, RAG/knowledge retrieval, exercises beyond the action-step library, notifications, reminders, subscriptions, payments, social sharing, or admin tooling.

- Q: Are generation state and plan lifecycle the same status, and how is async execution made operationally safe without Redis/a job queue? → A: They are **two independent concepts**, modeled as two separate enums. **GenerationStatus** (`PENDING | GENERATING | READY | FAILED`) tracks one generation attempt's progress; **PlanStatus** (`PROPOSED | ACTIVE | COMPLETED`) tracks the plan's lifecycle. ## 2. Scope

In scope (limited to behavior supported by the authoritative documents and the persisted feature-001 data):

- **Hybrid deterministic + LLM generation** of one personalized coaching plan per eligible user from the persisted profile and Assessment Result. AI/LLM personalization is a core capability of this feature.
- Idempotent generation start (no duplicate plans or duplicate provider calls on refresh, repeated requests, or reload); `FAILED` re-attempts on the same plan row.
- Plan content: a personalized title, a short current-focus summary, focus areas derived from the assessment, prioritized goals, small practical action steps, a suggested order, per-action completion status, a user-friendly reason per focus area, and an approved-scope disclaimer — all bilingual (Arabic + English), synthesized by the LLM and grounded/validated deterministically.
- **Explicit user acceptance** of the AI-generated plan before activation (Constitution IV): `PROPOSED → ACTIVE` via `POST /coaching/plan/accept`.
- Asynchronous generation with **two independent status concepts** — GenerationStatus (`PENDING | GENERATING | READY | FAILED`) and PlanStatus (`PROPOSED | ACTIVE | COMPLETED`) — and polling. A plan has no usable lifecycle/content until `generationStatus = READY` (which atomically sets `planStatus = PROPOSED`).
- Replacement of the `/dashboard` future-release placeholder with the coaching-plan experience, including generation/`PROPOSED`/accept/`FAILED`/ready states.
- Loading, empty, unavailable, and error dashboard states.
- Marking actions complete or incomplete (only when the plan is `ACTIVE`/`COMPLETED`); persisted, per-user progress and an overall plan-progress display; auto `ACTIVE ⇄ COMPLETED` lifecycle.
- Pinning each plan to its source assessment id, assessment definition version, result id, library version, disclaimer version, and prompt-template version; retaining historical plans without silent overwrite.
- Persisting generation/audit metadata (provider, model id, prompt/template version, source pins, generation status, validation outcome, retry count, safe usage metadata, timestamps) — **without** persisting hidden chain-of-thought.
- Backend-authoritative eligibility and routing (completed users receive the plan; incomplete users are routed to their authoritative next onboarding step; SAFETY_HOLD users remain in the safety flow and never enter generation).
- Pre-generation and post-generation deterministic safety checks; safe handling of concerning model output and provider failures.
- Ownership enforcement: a user can read and update only their own plan and actions; foreign identifiers are rejected by the backend.
- Full Arabic and English parity, including RTL/LTR, keyboard navigation, semantic HTML, accessible labels, focus handling, and screen-reader-friendly progress feedback. UI locale selects a stored translation and MUST NOT trigger a separate plan or provider call (generation is language-independent — always bilingual).
- Transactional, idempotent plan creation and progress updates with safe concurrent-update handling.

Explicit Non-Goals:

- AI-coach chat, coaching sessions, streaming responses, conversation memory, or RAG/knowledge retrieval. (The LLM is used for one-shot grounded plan synthesis, not conversation.)
- Medical diagnosis, treatment, crisis counselling, clinical recommendations, or medication advice.
- Notifications, reminders, subscriptions, payments, social sharing, gamification, streaks, and admin dashboards.
- Redesigning existing authentication, onboarding, assessment, safety, consent, or profile flows. This feature consumes their persisted state and routing; it does not alter them.
- Plan "pause" lifecycle, calendar-based scheduling with real dates, and AI-recommended exercise generation beyond the action-step library. (A suggested ordered sequence and optional pacing label are in scope; calendar scheduling and pausing are future.)
- Re-scoring or re-evaluating the assessment. The assessment result is consumed read-only.
- Pinning or hard-coding a specific LLM vendor in the spec; provider and model selection is configuration-driven. (Tests use deterministic fakes; automated tests MUST NOT call live paid providers.)

## 3. Assumptions

These are low-risk defaults consistent with the authoritative documents and the persisted feature-001 data. They are not material ambiguities; their product-decision status is recorded in §16.

A1 — Eligibility = `COMPLETED` and not `SAFETY_HOLD`: A user is eligible to receive a coaching plan only when `OnboardingState = COMPLETED` and a scored `AssessmentResult` exists whose gating `SafetyEvaluation` is `NORMAL` or `DISTRESS`. `COMPLETED` already excludes `SAFETY_HOLD` (feature 001 FR-018a/FR-019b), so eligibility reduces to "onboarding completed and a result exists." `DISTRESS` users completed onboarding via the normal path (feature 001 FR-018/FR-022) and are eligible; their plan reinforces the bounded, supportive framing already present in their assessment result.

A2 — Hybrid generation; Coaching owns the domain rule, AI module owns the provider adapter: Plan generation is a hybrid of deterministic rules and an LLM. The Coaching module owns the **generation domain rule**: eligibility, focus-area evidence computation, grounding-bundle assembly, structured-output validation, persistence, lifecycle, idempotency, concurrency, and safety boundaries. The AI module owns the **LLM provider adapter** and **prompt-template management**, exposed to Coaching through an app-owned provider port (`COACHING_LLM_PORT`, §7 FR-006a). The AI module does not import Coaching (no circular DI); the provider interface is owned by Coaching as the consumer (Constitution VIII). The LLM synthesizes a personalized bilingual plan grounded by the bundle; it MUST NOT decide eligibility/safety or invent clinical/medication/crisis content. This requires an SAD clarification/ADR (see §17): AI-assisted plan generation is a core Coaching-owned domain flow that invokes the AI module's provider adapter; the AI module MUST NOT bypass Coaching validation or ownership (Constitution IV).

A3 — One current plan per user; idempotent generation start: Generation is started idempotently the first time an eligible user opens the dashboard (or calls the plan endpoint) and the resulting plan is returned on every subsequent request. Creation is a conditional insert guarded by a unique "current plan per user" constraint, mirroring the assessment-submit idempotency pattern (feature 001 FR-015, research D6). Repeated requests, refreshes, reloads, and re-logins return the existing plan and MUST NOT create duplicates or trigger duplicate provider calls; a `generationStatus = FAILED` plan is retried on the **same row** via a new attempt (A14, A18).

A4 — Explicit accept-then-activate (AI-generated, so acceptance is required): Because the plan is AI-generated, Constitution IV's "explicit user acceptance before activation" is **actively engaged** (not vacuous). Generation produces a plan with `generationStatus = READY` and `planStatus = PROPOSED` (set **atomically** on successful validation; A14). The plan becomes `ACTIVE` only when the user explicitly accepts it via `POST /coaching/plan/accept`, which transitions **only** `planStatus: PROPOSED → ACTIVE` (it does not touch `generationStatus`). Action tracking (`PATCH`) is enabled only when `generationStatus = READY` and the plan is `ACTIVE` or `COMPLETED`. No separate "activate" step beyond accept, no separate "mark complete" control, and no "pause" are introduced. Constitution V's lifecycle-status and completion-rule requirements are met with a minimal `PROPOSED → ACTIVE ⇄ COMPLETED` lifecycle driven automatically by action progress **after** acceptance (see A5).

A5 — Minimal lifecycle (post-acceptance, PlanStatus only): `PROPOSED → ACTIVE ⇄ COMPLETED`, auto-driven by action progress. A plan enters `PROPOSED` when `generationStatus` becomes `READY` (A14), and enters `ACTIVE` on explicit acceptance (A4). It auto-transitions to `COMPLETED` when **all** of its action steps are complete; if any action is later reopened, it auto-transitions back to `ACTIVE`. These lifecycle transitions touch **only `planStatus`** — they never change `generationStatus`. There is **no separate "Mark plan complete" control** — completion status is derived solely from action progress. Action-level completion is tracked independently and rolls up into overall progress. `PAUSE` and time-bound calendar scheduling are deferred to a future feature (out of scope here). Overall progress = completed actions / total actions across the plan.

A6 — Focus-area evidence rule (deterministic, supplied to the LLM): Focus-area evidence is derived deterministically from the Assessment Result in a fixed priority order: (1) the user's selected priorities (AG-01/AG-02, in ranked order), (2) the `support_domain` (the domain most in need of support), (3) the lowest-banded remaining domains, deduplicated, capped at three focus areas. This deterministic evidence is part of the grounding bundle supplied to the LLM; the LLM personalizes the per-focus-area reason and copy, bounded by the grounding and validation (A7, FR-010a). The LLM does not redefine which focus areas apply; the deterministic evidence defines them.

A7 — Grounding library + disclaimer are required, approved, versioned inputs that bound and constrain the LLM: The CoachingActionLibrary and CoachingDisclaimer are approved, versioned, bilingual reference content (like the Assessment/Safety definition tables in feature 001). They are **grounding sources**, not a pick-list: the LLM may synthesize personalized copy, but every goal and action it emits MUST reference an approved `libraryKey` present in the pinned library version; the deterministic validator rejects any `libraryKey` not in the pinned version. The CoachingActionLibrary is a **required implementation input**: the feature cannot ship without approved library content for every focus area it can produce. The specification and implementation MUST NOT invent, draft, or hard-code clinical, diagnostic, medication, or otherwise unsupported coaching content as a substitute for the approved library; missing or unapproved library content, missing disclaimer, provider failure, malformed output, validation failure, or concerning output all fail closed to the `FAILED`/unavailable state rather than presenting fabricated copy. The library content and the disclaimer copy are approved-for-planning; final clinical/legal sign-off of the CoachingActionLibrary content and the coaching-scope disclaimer is a launch gate (§16), as are prompt-template review (Constitution III) and provider data-retention/training policy review (Constitution VI).

A8 — Suggested order, not calendar dates: The "suggested schedule" is an ordered sequence of focus areas and, within each, an ordered sequence of action steps, with an optional short pacing label (for example, "start here" / "next" / "when ready") synthesized within approved bounds. No real calendar dates, deadlines, or reminders are produced.

A9 — Assessment retakes are not currently possible but are defined safely: Feature 001 disallows retakes after `COMPLETED` (FR-018a). To satisfy the explicit requirement to define safe retake behavior, this feature pins every plan to its source `assessment_id`, `definition_version`, `result_id`, `library_version`, `disclaimer_version`, and `prompt_version`, and treats plans as immutable once created. A future retake that produces a new `AssessmentResult` MUST NOT silently overwrite the existing plan; a retake triggers a new generation that creates a new current plan for the new scored result and preserves historical plans (immutable). The current feature implements one-current-plan generation only; the retake UI is a defined, safe boundary for the future retake feature, not a built UI in this feature.

A10 — Private assessment data is not echoed (in responses or to the provider): The plan API responses expose the derived plan (title, summary, focus areas, goals, actions, reasons, disclaimer, progress) and the source assessment version/result identifiers only. They do NOT expose raw assessment answers, free-text answers, raw domain scores, safety answers, or safety levels. The grounding bundle sent to the LLM carries only the deterministic evidence (domain codes/bands, `strongestDomain`, `supportDomain`, selected priorities as **codes**, plus the minimum profile fields needed, the library, the disclaimer, and the generation instructions) — NO raw answers, NO free-text (user-authored `goalFreeText` is excluded by default pending a privacy review), NO safety data. The plan is the user-facing distillation; the underlying assessment data remains private (Constitution VI/VII).

A11 — Routing reuses the existing authoritative mechanism: Dashboard eligibility and routing reuse the existing `GET /onboarding/state` `next_route` and `GET /onboarding/completion` `post_onboarding_route` contract from feature 001. `COMPLETED` users reach `/dashboard` (the plan); incomplete users are redirected to their `next_route` unfinished step; `SAFETY_HOLD` users are routed to `/safety/hold`. No new routing authority is introduced; the `RequireOnboarding` guard continues to be UX-only, with the backend authoritative (feature 001 FR-028/FR-033).

A12 — Concurrency and idempotency reuse the established pattern: Plan creation and action-progress updates use conditional updates and unique constraints, the same approach feature 001 uses for assessment submit and onboarding transitions (research D6, spec §7). Progress updates are scoped to a single action and validated for ownership and action-id belonging before any write.

A13 — Provider abstraction: The LLM is accessed only through an app-owned provider port `COACHING_LLM_PORT` (`CoachingLlmPort { generatePlan(bundle): Promise<LlmPlanResult> }`), owned by Coaching; the AI module supplies the adapter (config-driven provider/model selection; secrets remain server-side; token, latency, timeout, rate-limit, and cost controls). Automated tests use a deterministic fake adapter (`FakeCoachingLlmAdapter`) and MUST NOT call live paid providers (Constitution VI; §16 launch gate). The domain is not coupled to one vendor (Constitution "AI and RAG" standards).

A14 — Generation lifecycle (async start + poll, no new infrastructure; two independent statuses): Generation runs in-process with state persisted to the database (no job queue, no Redis). Status is **two independent concepts**: **GenerationStatus** (`PENDING | GENERATING | READY | FAILED`) — the progress of one generation attempt, a column on `CoachingPlan` and on each `CoachingPlanGeneration` attempt row — and **PlanStatus** (`PROPOSED | ACTIVE | COMPLETED`) — the plan's lifecycle, a column on `CoachingPlan` that is `null` until generation succeeds. A plan has no usable lifecycle/content until `generationStatus = READY`. On successful validation, the system transitions `generationStatus → READY` and `planStatus → PROPOSED` **atomically** (one transaction). `POST /coaching/plan` idempotently creates or returns the current plan and returns `202` while `generationStatus` is `PENDING`/`GENERATING`; it returns the existing resource **without invoking the provider** when `generationStatus = READY`; on `generationStatus = FAILED` it triggers a retry (A18). `GET /coaching/plan` returns `generationStatus` during generation; when `READY` it also returns `planStatus` and usable plan content; when `FAILED` it returns a safe retryable failure representation. There is no `GET /coaching/plan/:id` — the current plan is resolved server-side by `userId` (JWT-only ownership). Provider/validation failure transitions `generationStatus → FAILED` (it is **not** a `PlanStatus`); no usable plan content is persisted. Retry changes `generationStatus: FAILED → PENDING` on the **same current plan record** and creates a **new** `CoachingPlanGeneration` attempt row (the prior `FAILED` attempt row is retained for audit). A UI locale change transitions neither status and never invokes generation.

A15 — Generation metadata and auditability: Each generation attempt is recorded in a `CoachingPlanGeneration` audit row: attempt number, provider, model id, prompt/template version, source assessment id/result id/definition version, library version, disclaimer version, generation status, validation outcome (sanitized), retry count, token usage, latency, `started_at`, `deadline_at` (lease expiry for that attempt), `finished_at`, and a sanitized error code. The parent `CoachingPlan` row also carries lease metadata for the in-flight attempt (`generationStartedAt`, `generationDeadlineAt`) and a `currentAttemptId` reference to the `CoachingPlanGeneration` row being worked, used to discard late results from expired attempts (A18). **No hidden chain-of-thought is persisted**; only the necessary inputs (references, not raw content), outputs (references to the validated plan), and operational metadata are stored, per the project's privacy requirements (Constitution VI). One row per attempt.

A18 — Operationally-safe async execution (lease + reclaim; no fire-and-forget): The MVP keeps async start + poll without Redis or a job queue, but generation MUST NOT rely on an untracked fire-and-forget Promise after the HTTP response. The execution model:
- **Atomic generation claim**: the `PENDING → GENERATING` transition is a single conditional update (`UPDATE CoachingPlan SET generationStatus='GENERATING', generationStartedAt=now(), generationDeadlineAt=now()+lease, currentAttemptId=:attemptId WHERE id=:planId AND generationStatus='PENDING'`); only one worker/request can succeed, so simultaneous retries/claims never start duplicate provider calls.
- **Tracked in-process runner**: a singleton generation runner (owned by the Coaching module) holds a registry of in-flight attempts (by `planId`/`currentAttemptId`) with their AbortSignals, so the work is observable and cancelable — not an untracked Promise. The runner is triggered by `POST` (start) and by `GET`/`POST` reclaim when a stale `GENERATING` attempt is detected.
- **Lease metadata**: each in-flight attempt has `generationStartedAt` + `generationDeadlineAt` (the configured lease). An attempt is considered stale once `now() > generationDeadlineAt`.
- **Stale recovery**: on `GET`/`POST`, if `generationStatus = 'GENERATING'` and `now() > generationDeadlineAt`, the attempt is reclaimed — the stale `CoachingPlanGeneration` attempt row is marked `FAILED` with a sanitized `TIMEOUT`/`STALE` error code, and `generationStatus` returns to `PENDING` so a new claim can proceed (the user polls again or a retry starts a new attempt). This also recovers from **process restart**: in-flight tracked promises are lost on restart, but the plan row remains `GENERATING` with a deadline; the next `GET`/`POST` after the deadline reclaims it. No manual intervention is required.
- **Retry**: a `POST` while `generationStatus = FAILED` (or a reclaim) transitions `generationStatus: FAILED → PENDING` on the **same current plan record** and creates a **new** `CoachingPlanGeneration` attempt row; the worker then claims it. No new `CoachingPlan` row is created for a retry.
- **Late-result guard**: when a worker finishes an attempt (success or failure), it persists only via a conditional update guarded on `generationStatus = 'GENERATING' AND currentAttemptId = :thisAttemptId`. If a newer attempt has already been claimed (or the plan is already `READY`), `currentAttemptId` no longer matches → the late result updates zero rows and is **discarded**; a late success from an expired attempt can never overwrite a newer successful attempt.
- **Provider timeout**: handled per the adapter config (FR-006a); on timeout the attempt transitions `generationStatus → FAILED` (treated as a reclaimable failure) and a retry creates a new attempt.
- **Duplicate POST**: returns the same plan and never duplicates an active provider call — if `generationStatus` is already `GENERATING` (lease alive), `POST` returns `202` and starts nothing; if `READY`, returns the resource without a provider call; if `PENDING`, the atomic claim ensures at most one call.
- **Runtime prerequisite**: this in-process model requires the API process to be a **long-running containerized NestJS service** (the deployment per plan.md) so the tracked runner survives between the `202` response and attempt completion. If the deployment were serverless or scaled the API process to zero between requests, the in-process runner could not survive and the execution-trigger mechanism would be **NEEDS CLARIFICATION** (it would require a real queue); under the current long-running container deployment this is **not** a blocker.

A16 — Safety boundary (pre- and post-generation): SAFETY_HOLD/HIGH_RISK/CRISIS users never enter ordinary coaching-plan generation (pre-generation eligibility + safety gate). A deterministic post-generation safety check validates the LLM output for scope (no clinical/diagnostic/medication/crisis content; concerning-output detection) and rejects unsafe output to `FAILED`. `DISTRESS` users are eligible; the generation instructions enforce bounded supportive framing. All paths fail closed. The Constitution II AI safety pipeline (pre-generation risk assessment, permitted-path selection, AI generation only when permitted, post-generation safety validation, delivery/blocking) is actively exercised.

A17 — Privacy boundary to the provider: Only the minimum context required for plan generation is shared with the LLM provider (Constitution VI/VII): the deterministic assessment evidence (codes/bands, not raw data), the minimum profile fields, the pinned library content, the disclaimer, and the generation instructions. No raw answers, no free-text, no safety data, no conversation history/memory. The provider's data-retention and training policy MUST be reviewed and documented before production use (launch gate, §16; Constitution VI).

## 4. Prioritized User Stories and Acceptance Scenarios

User stories are ordered by priority and are independently testable: implementing any P1 story alone yields a verifiable, valuable slice. Acceptance scenarios use Given/When/Then.

### User Story 1 — An eligible user receives their personalized coaching plan on the dashboard (Priority: P1)

An authenticated user who completed onboarding and the assessment opens the dashboard, generation starts, and they see a personalized, non-clinical coaching plan synthesized by the LLM from their assessment result, replacing the future-release placeholder. The plan is `PROPOSED` until the user accepts it.

**Why this priority**: This is the core deliverable of the feature and the primary user story in the input. Without it the placeholder remains and no value is delivered. (Constitution I, V; PRD §7 step 5; PRD §8 Coaching Plan.)

**Independent Test**: An eligible user (onboarding `COMPLETED`, scored result, not `SAFETY_HOLD`) opens `/dashboard`, `POST /coaching/plan` starts generation (`202`, `generationStatus = PENDING`), polling reaches `generationStatus = READY` (which atomically sets `planStatus = PROPOSED`), and the plan is displayed with a title, summary, focus areas, goals, ordered actions, per-action status, a per-focus-area reason, and a disclaimer — without any other story being implemented.

**Acceptance Scenarios**:

1. **Given** an authenticated user whose `OnboardingState = COMPLETED` with a scored `AssessmentResult`, **When** they open `/dashboard`, **Then** generation starts (`POST /coaching/plan` → `202`, `generationStatus = PENDING`), the future-release placeholder is replaced by the coaching-plan experience, and a personalized plan is synthesized (grounded + validated) and persisted (`generationStatus → READY`, `planStatus → PROPOSED` atomically).
2. **Given** an eligible user's plan was just generated, **When** the plan is displayed (`generationStatus = READY`, `planStatus = PROPOSED`), **Then** it contains a personalized title, a short current-focus summary, focus areas derived from the assessment, prioritized goals, small practical action steps, a suggested order, per-action completion status (initially incomplete), a user-friendly non-clinical reason for each focus area, and an approved-scope disclaimer — all bilingual (Arabic + English).
3. **Given** an eligible user, **When** they reload `/dashboard` or log in again later, **Then** the same existing plan is returned; no duplicate plan is created and no duplicate provider call is made.
4. **Given** a `READY`/`PROPOSED` plan, **When** the user explicitly accepts it (`POST /coaching/plan/accept`), **Then** `planStatus` transitions to `ACTIVE` (only `planStatus` changes; `generationStatus` stays `READY`) and action tracking becomes available.
5. **Given** a plan is displayed, **When** the user reads it, **Then** it explicitly states it is not a medical diagnosis, clinical conclusion, or substitute for professional care, and contains no diagnosis, medication advice, or unsupported claim.

**Failure / Safety Scenarios**:

- **Given** an eligible user, **When** generation cannot produce a valid plan (provider failure, malformed/empty output, validation failure, missing/corrupt/unapproved grounding, or concerning output), **Then** the system MUST NOT fabricate or persist a usable plan; `generationStatus` transitions to `FAILED` (`planStatus` is not set), the dashboard shows the "unavailable" state with retry, and a retry changes `generationStatus: FAILED → PENDING` on the same plan row and creates a new `CoachingPlanGeneration` attempt (Constitution III/IV; A18; feature 001 US5 failure-path precedent).

### User Story 2 — The user accepts the plan, tracks progress by completing and reopening action steps, and progress persists (Priority: P1)

The user accepts the `PROPOSED` plan, then marks action steps complete or incomplete, sees overall plan progress, and the progress persists across reloads and login sessions.

**Why this priority**: Explicit acceptance is required for AI-generated plans (Constitution IV), and trackable progress is a Constitution V requirement for every active coaching plan and the primary engagement loop the dashboard replaces the placeholder with. (Constitution IV/V; PRD §8 Goals/Exercises.)

**Independent Test**: A user with a `PROPOSED` plan accepts it (→ `ACTIVE`), marks an action complete, sees overall progress update, reloads, and still sees the action complete and the same overall progress — without plan generation being re-implemented.

**Acceptance Scenarios**:

1. **Given** a user viewing their `PROPOSED` plan, **When** they accept it (`POST /coaching/plan/accept`), **Then** the plan transitions to `ACTIVE` and action tracking is enabled.
2. **Given** an `ACTIVE` plan, **When** the user marks an action step complete, **Then** the action's status becomes complete, the overall plan progress reflects it, and the update is persisted.
3. **Given** a completed action, **When** the user marks it incomplete again, **Then** the status returns to incomplete and overall progress recomputes.
4. **Given** a user with completed actions, **When** they reload `/dashboard` or log out and back in, **Then** all prior action statuses and the overall progress are restored unchanged.
5. **Given** a plan with N actions, **When** the user completes K of them, **Then** overall progress is reported as K/N and is conveyed to screen readers as feedback (not only visually).
6. **Given** an `ACTIVE` plan whose last incomplete action is marked complete, **When** all actions are now complete, **Then** the plan auto-transitions to `COMPLETED` without any separate "mark plan complete" action by the user, and the new status is persisted and surfaced.
7. **Given** a `COMPLETED` plan, **When** the user reopens (marks incomplete) any action, **Then** the plan auto-transitions back to `ACTIVE` and overall progress recomputes, with no separate user action required.

**Failure / Safety Scenarios**:

- **Given** a progress update attempted while `generationStatus ≠ READY` (e.g. `PENDING`/`GENERATING`/`FAILED`), **When** it is submitted, **Then** the backend rejects it (`409 PLAN_NOT_READY`) and no progress changes; the plan is not yet generated.
- **Given** a progress update attempted on a `PROPOSED` plan (`generationStatus = READY` but `planStatus ≠ ACTIVE`/`COMPLETED`), **When** it is submitted, **Then** the backend rejects it (`409 PLAN_NOT_ACTIVE`) and no progress changes; the plan must be accepted first.
- **Given** a progress update, **When** the action identifier does not belong to the user's plan, **Then** the backend rejects it and no progress changes (see US5).
- **Given** two concurrent updates to the same action from multiple tabs, **When** both are submitted, **Then** each update is applied atomically; no lost update corrupts progress and the final state is one of the two submitted states (optimistic-concurrency/conditional-update, feature 001 §7 precedent).

### User Story 3 — Incomplete users are routed to their authoritative next step; SAFETY_HOLD users stay in safety (Priority: P1)

A user who has not completed onboarding is routed to their backend-authoritative next onboarding step; a SAFETY_HOLD user remains in the existing safety flow and never enters plan generation.

**Why this priority**: Safety takes precedence over feature completion, and the backend is authoritative for eligibility and routing (Constitution II; input §1). This guards the plan from being shown to ineligible or unsafe users and ensures the LLM is never invoked for them.

**Independent Test**: An incomplete user navigating to `/dashboard` is redirected to their `next_route` unfinished step; a `SAFETY_HOLD` user is redirected to `/safety/hold` and cannot start generation via the API — without plan UI being implemented.

**Acceptance Scenarios**:

1. **Given** an authenticated user whose onboarding is not `COMPLETED`, **When** they navigate to `/dashboard`, **Then** they are redirected to their authoritative `next_route` unfinished onboarding step (reusing feature 001 `RequireOnboarding` + `GET /onboarding/state`).
2. **Given** an authenticated user in `SAFETY_HOLD`, **When** they navigate to `/dashboard`, **Then** they are routed to `/safety/hold` and never see a coaching plan.
3. **Given** a `SAFETY_HOLD` user, **When** they call the plan API directly, **Then** the backend returns the safety-hold routing error and starts no generation (FR-019b precedent; backend authoritative, route guards UX-only). SAFETY_HOLD/HIGH_RISK/CRISIS never enter generation.
4. **Given** an authenticated user with no completed assessment result, **When** they reach the plan endpoint, **Then** the backend returns a "not available" response and starts no generation; the dashboard shows the "empty/unavailable" state, never a fabricated plan.

**Failure / Safety Scenarios**:

- **Given** the onboarding state cannot be determined, **When** the user reaches `/dashboard`, **Then** they are routed to the earliest unfinished step rather than assuming completion (feature 001 US9 failure-path precedent).

### User Story 4 — The plan is fully localized in Arabic and English with correct RTL/LTR and is accessible (Priority: P1)

The plan renders naturally in both Arabic and English with correct directionality, keyboard operability, semantic structure, and screen-reader-friendly progress, with no hard-coded user-facing strings. A UI locale switch selects a stored translation and never triggers a separate plan or provider call.

**Why this priority**: First-class bilingual equality and accessibility are constitutional requirements (Constitution X; Frontend §12/§13). The plan is the primary post-onboarding surface, so it must meet these from day one. Generation is language-independent (always bilingual); the locale only selects which stored translation to render.

**Independent Test**: Switching the user's language to Arabic re-renders the entire plan — title, summary, focus areas, goals, actions, reasons, disclaimer, progress, and all states — in natural Arabic and RTL, with keyboard-only operability and screen-reader progress announcements, without any new generation or provider call.

**Acceptance Scenarios**:

1. **Given** a user whose preference is Arabic, **When** they view their plan, **Then** all plan content and states render in natural Arabic with RTL direction, including mixed Arabic/English/numbers.
2. **Given** a user whose preference is English, **When** they view their plan, **Then** all content renders in English with LTR direction.
3. **Given** any plan screen, **When** the user switches language, **Then** direction (RTL/LTR) and every localized string update without losing plan or progress data, without starting a new generation or provider call, and without changing `generationStatus` or `planStatus` (a locale change transitions neither status).
4. **Given** a plan view, **When** the user navigates by keyboard alone, **Then** all interactive controls (accept control, action toggles) are reachable in a logical order with visible focus and correct labels, in both LTR and RTL.
5. **Given** progress changes, **When** an action is toggled, **Then** screen-reader users receive an updated progress announcement (for example, "2 of 5 actions complete") via an accessible live region, not only a visual bar.

**Failure / Safety Scenarios**:

- **Given** a localized string is missing for one language, **When** the plan renders, **Then** a defined fallback is shown; the system MUST NOT silently fall back to the other language for safety-relevant content (the disclaimer) without a documented rule (feature 001 §12 precedent).

### User Story 5 — Users cannot read or modify another user's plan (Priority: P1)

A user can read and update only their own plan and action steps; foreign action identifiers and cross-user access are rejected by the backend. The current plan is resolved server-side by `userId`; there is no `GET /coaching/plan/:id`.

**Why this priority**: User-data isolation is non-negotiable; the plan and its progress are sensitive, user-owned records (Constitution VI; feature 001 FR-027..FR-029). Frontend route guards are not a security boundary.

**Independent Test**: A user supplying another user's plan id or action id, or calling the plan endpoint without eligibility, is rejected by the backend and no foreign data is returned or modified — without UI being implemented.

**Acceptance Scenarios**:

1. **Given** an authenticated user, **When** they call the plan API, **Then** the backend returns only the plan owned by that user, scoped by `user_id` (resolved server-side; no plan-id param accepted); no other user's plan is reachable.
2. **Given** an authenticated user, **When** they submit a progress update with an action identifier that does not belong to their current plan, **Then** the backend rejects it (404/403) and no progress changes.
3. **Given** an authenticated user, **When** they attempt to supply a foreign plan id or another user's identifier in any request, **Then** the backend ignores client-supplied ownership identifiers and authorizes solely from the verified session.
4. **Given** any plan or progress payload, **When** it is processed, **Then** plan and progress content MUST NOT appear in application logs, analytics, traces, or error reports (feature 001 FR-030 precedent). Generation metadata stores no chain-of-thought and no raw assessment content.

**Failure / Safety Scenarios**:

- **Given** a missing or invalid authentication session, **When** the plan API is called, **Then** the request is rejected with the standard auth error; no plan data is returned.

### User Story 6 — Existing onboarding, assessment, safety, and dashboard behavior has no regressions (Priority: P2)

Replacing the dashboard placeholder and adding AI-personalized plan generation does not regress existing authentication, onboarding, assessment, safety, or routing behavior.

**Why this priority**: The feature consumes persisted state and routing from feature 001; regressions there would break the whole journey. It is P2 because it is a guardrail verified across the integrated flow rather than a standalone value slice. (Constitution IX; Frontend §7.)

**Independent Test**: The full feature-001 journey still works end-to-end, and the only observable change at `/dashboard` is that completed eligible users now see a plan (with generation/accept states) instead of the placeholder.

**Acceptance Scenarios**:

1. **Given** a new user, **When** they run the feature-001 onboarding journey to completion, **Then** they land on `/dashboard` and see the coaching plan (no placeholder, no regression in prior steps).
2. **Given** an incomplete or `SAFETY_HOLD` user, **When** they interact with onboarding/assessment/safety flows, **Then** those flows behave exactly as in feature 001 (no plan is shown, no generation is started, routing unchanged).
3. **Given** a returning completed user, **When** they log in, **Then** they are routed to `/dashboard` via the existing `post_onboarding_route` and see their existing plan.

**Failure / Safety Scenarios**:

- **Given** the plan subsystem (or the LLM provider) is unavailable, **When** a completed user opens `/dashboard`, **Then** the dashboard shows the `FAILED`/unavailable state with retry and the rest of the app remains usable (no global breakage); no fabricated plan is shown.

## 5. Independently Testable Acceptance Scenarios (cross-cutting)

AC-X1 (Eligibility is independently testable): Fixtured onboarding/result states — `COMPLETED` with a scored result, incomplete, `SAFETY_HOLD`, and no result — produce the correct plan-available vs. routed vs. unavailable behavior. Eligibility is deterministic and does not invoke the LLM.

AC-X2 (Idempotent generation is independently testable): A repeated plan generation start for the same eligible user yields exactly one plan and triggers at most one provider call; repeated/concurrent calls do not create duplicates or duplicate provider calls; a `FAILED` plan is re-attempted on the same row.

AC-X3 (Reproducibility + grounding is independently testable): The same grounding bundle + the same deterministic fake provider produce the same validated plan (same focus areas, goals, actions, order, reasons) every time, via fixtures, independent of the UI. Deterministic components (eligibility, focus-area evidence, validation) are reproducible; production LLM output is non-deterministic but is validated and grounded (allowed library ids enforced) before persistence. Tests use fakes; automated tests do not call live paid providers.

AC-X4 (Progress isolation is independently testable): A user cannot read or update another user's plan or actions; foreign action ids are rejected; authorization is enforced server-side.

AC-X5 (Concurrency is independently testable): Concurrent progress updates to the same action resolve to a single consistent state with no lost update; updates to different actions do not interfere.

AC-X6 (Source pinning is independently testable): Every persisted plan records its source `assessment_id`, `definition_version`, `result_id`, `library_version`, `disclaimer_version`, and `prompt_version`; a new assessment result never silently overwrites an existing plan.

AC-X7 (Localization/RTL is independently testable): The plan and all its states render correctly in Arabic/RTL and English/LTR, including progress announcements, via tests and not only by setting `dir`. A locale switch never triggers a new generation or provider call.

AC-X8 (No-regression is independently testable): The feature-001 journey and routing behave unchanged except that completed eligible users see a plan at `/dashboard`.

AC-X9 (Lifecycle is auto-driven and independently testable): An `ACTIVE` plan with all actions complete is `COMPLETED`; reopening any action returns it to `ACTIVE`; no separate "mark plan complete" control exists in the UI or API. The transition is derived solely from action progress and occurs only after the plan is accepted.

AC-X10 (Explicit acceptance is independently testable): A generated plan has `generationStatus = READY` and `planStatus = PROPOSED`; `planStatus` becomes `ACTIVE` only via `POST /coaching/plan/accept` (which does not change `generationStatus`); acceptance is allowed only when `generationStatus = READY` and `planStatus = PROPOSED`; `PATCH` actions are rejected unless `generationStatus = READY` and `planStatus` is `ACTIVE`/`COMPLETED`; acceptance of a `PENDING`/`GENERATING`/`FAILED` plan is rejected (`409 PLAN_NOT_READY`/`PLAN_UNAVAILABLE`), and acceptance is blocked if the user has entered `SAFETY_HOLD` after generation; acceptance of an already-`ACTIVE`/`COMPLETED` plan is an idempotent no-op success.

AC-X11 (Generation lifecycle is independently testable): GenerationStatus transitions `PENDING → GENERATING → READY` (success, atomically setting `planStatus = PROPOSED`) or `→ FAILED` (provider failure, malformed output, validation failure, missing grounding, or concerning output); a `FAILED` plan persists no usable plan content and is retried on the **same row** by transitioning `generationStatus: FAILED → PENDING` and creating a **new** `CoachingPlanGeneration` attempt row; `GET /coaching/plan` returns `generationStatus` during generation, returns `planStatus` + usable content when `READY`, and returns a safe retryable failure representation when `FAILED`. `FAILED` is a GenerationStatus, never a PlanStatus.

AC-X12 (Generation auditability is independently testable): Each attempt records a `CoachingPlanGeneration` row (attempt, provider, model id, prompt/template version, source pins, status, validation outcome, retry count, token usage, latency, `started_at`, `deadline_at`, `finished_at`, sanitized error code) and stores NO chain-of-thought and NO raw assessment content; the parent plan carries lease metadata (`generationStartedAt`, `generationDeadlineAt`) and `currentAttemptId`.

AC-X13 (Async execution safety is independently testable): The `PENDING → GENERATING` transition is an atomic conditional claim — concurrent claims/retries start at most one provider call; duplicate `POST` requests return the same plan and never duplicate an active provider call; a stale `GENERATING` attempt past `generationDeadlineAt` is reclaimed (`generationStatus → PENDING`, stale attempt `FAILED` with `TIMEOUT`/`STALE`); retry operates on the same plan row and creates a new attempt; a late result from an expired attempt cannot overwrite a newer successful attempt (the success update is guarded on `currentAttemptId`); process restart is recovered lazily via the lease on the next `GET`/`POST`.

## 6. Edge Cases

- **No completed assessment**: Eligibility fails; no generation starts; the dashboard shows the "empty/unavailable" state; the user is not presented a fabricated plan.
- **Missing or inconsistent assessment result** (for example, a result row exists but domain scores/bands are absent or corrupted): The deterministic rules MUST NOT assemble a grounding bundle from a corrupt result; no generation starts; the dashboard shows "unavailable"; creation fails closed (Constitution III, feature 001 US5 precedent).
- **Unsupported or unknown assessment-result values** (a domain band outside the approved set, or a result produced by an unknown assessment version): Treated as "cannot classify"; no generation starts; "unavailable" state; the unsupported value is not echoed to the user and not sent to the LLM.
- **Missing, corrupt, or unapproved grounding** (library or disclaimer): Discovered before the provider call → `503 PLAN_UNAVAILABLE`; no provider call; no plan persisted; "unavailable" state with retry.
- **Provider failure, malformed/empty output, validation failure, or concerning output**: `generationStatus` transitions to `FAILED` (`planStatus` is not set); no usable plan is persisted; `GET /coaching/plan` returns a safe retryable failure representation (`503 PLAN_UNAVAILABLE` with `generationStatus: FAILED`, `retryable: true`); the dashboard shows "unavailable" with retry; a retry changes `generationStatus: FAILED → PENDING` on the same `CoachingPlan` row and creates a **new** `CoachingPlanGeneration` attempt row (the prior `FAILED` attempt row retained for audit). Concerning output (clinical/diagnostic/medication/crisis/scope violation) is rejected by the post-generation safety validation.
- **Repeated generation requests / refresh / reload / new login**: The existing plan is returned (or its current `generationStatus` during generation); no duplicate is created and no duplicate provider call is made; the idempotent start is guarded by the unique "current plan per user" constraint, a conditional insert, and the atomic generation claim (A18).
- **Stale `GENERATING` attempt (process restart, lost worker, or long provider call)**: If `generationStatus = GENERATING` and `now() > generationDeadlineAt`, the attempt is reclaimed on the next `GET`/`POST`: the stale `CoachingPlanGeneration` attempt row is marked `FAILED` (`TIMEOUT`/`STALE`), `generationStatus` returns to `PENDING`, and a new attempt can be claimed. No manual intervention is required (A18).
- **Late result from an expired attempt**: A worker that finishes after its lease expired (or after a newer attempt was claimed) persists only via a conditional update guarded on `currentAttemptId`; if a newer attempt exists, the update matches zero rows and the late result is discarded — it can never overwrite a newer successful attempt (A18).
- **Simultaneous retries / concurrent claims**: The atomic `PENDING → GENERATING` conditional claim ensures only one worker starts a provider call; concurrent claims on the same plan see `GENERATING` (or fail the claim) and return the existing status — never a duplicate active call (A18).
- **Existing plan after reload or a new login**: The persisted plan and all action statuses are returned unchanged; progress is restored.
- **Assessment retakes** (future; not currently possible per feature 001 FR-018a): A new `AssessmentResult` MUST NOT silently overwrite the existing plan. The existing plan remains pinned to its original source. A retake triggers a new generation that creates a new current plan for the new scored result and preserves historical plans (immutable); only one plan is "current" per user at a time.
- **Partial or failed plan creation**: Plan creation is transactional — either the plan with all its focus areas, goals, actions, source pins, and generation metadata is persisted (`generationStatus → READY`, `planStatus → PROPOSED` atomically), or nothing usable is. A `FAILED`/partial state persists no usable plan content (only the `CoachingPlan` row at `generationStatus = FAILED` + the `CoachingPlanGeneration` audit row). A retry re-attempts cleanly on the same row via a new attempt.
- **Concurrent progress updates**: Updates to the same action are serialized via conditional update / optimistic concurrency; the final state is one of the submitted states with no corruption. Updates to different actions do not block each other unnecessarily.
- **Invalid or foreign action identifiers**: A progress update referencing an action id that does not belong to the user's current plan is rejected; no progress changes; the client is guided to refresh its plan view.
- **Acceptance timing**: Accepting a plan whose `generationStatus` is `PENDING`/`GENERATING` → `409 PLAN_NOT_READY`. Accepting a `generationStatus = FAILED` plan → `409 PLAN_UNAVAILABLE` (retry generation first). Accepting an already-`ACTIVE`/`COMPLETED` plan is an idempotent no-op success. A `PATCH` while `generationStatus ≠ READY` → `409 PLAN_NOT_READY`; a `PATCH` on a `PROPOSED` plan (`generationStatus = READY`, `planStatus ≠ ACTIVE`/`COMPLETED`) → `409 PLAN_NOT_ACTIVE`.
- **SAFETY_HOLD users**: Never enter generation; the plan API returns the safety-hold routing error and starts no generation; the dashboard route redirects to `/safety/hold`. Even if a plan existed from a prior completed state (not currently possible from feature 001, but defined defensively), the backend MUST NOT serve a normal plan or accept it while `OnboardingState = SAFETY_HOLD` (acceptance blocked → `409 SAFETY_HOLD`).
- **Client-supplied ownership or plan ids**: The backend ignores client-supplied user/plan ownership in mutating requests and authorizes from the verified session only; foreign ids are not trusted. There is no `GET /coaching/plan/:id`.
- **Language switch mid-plan**: Re-renders the entire plan and all states from the stored bilingual payload in the new language and direction without losing progress, without starting a new generation or provider call, and without changing `generationStatus` or `planStatus` (feature 001 FR-011 precedent).
- **Missing localized string**: Defined fallback; no silent cross-language fallback for the disclaimer (feature 001 §12 precedent).
- **Plan subsystem or LLM provider unavailable**: Dashboard shows the `FAILED`/error/unavailable state with a retry; no fabricated plan; the rest of the app remains usable. Provider timeout/retry is configuration-driven; a provider timeout transitions `generationStatus → FAILED` (reclaimable) on the current attempt.

## 7. Functional Requirements

Stable IDs. Each requirement is testable. "MUST" denotes a non-negotiable requirement.

### Eligibility and Routing

- **FR-001**: The system MUST generate and serve a coaching plan only to an authenticated user whose `OnboardingState = COMPLETED` and who has a scored `AssessmentResult` whose gating `SafetyEvaluation` is `NORMAL` or `DISTRESS`.
- **FR-002**: The backend MUST be authoritative for plan eligibility and routing; frontend route guards MUST NOT be treated as a security boundary (feature 001 FR-028).
- **FR-003**: An authenticated user whose onboarding is not `COMPLETED` MUST be redirected to their authoritative `next_route` unfinished onboarding step when they reach `/dashboard` (reusing `GET /onboarding/state`).
- **FR-004**: An authenticated user in `SAFETY_HOLD` MUST be routed to `/safety/hold`, MUST NOT receive a normal coaching plan via the UI or the API, and MUST NOT enter plan generation. SAFETY_HOLD/HIGH_RISK/CRISIS never enter generation.
- **FR-005**: The system MUST reuse the existing `GET /onboarding/completion` `post_onboarding_route` (`/dashboard`) so completed users land on the plan without new routing authority.

### Plan Generation (Hybrid Deterministic + LLM)

- **FR-006**: Plan generation MUST be a hybrid of deterministic rules and an LLM. The deterministic rules MUST be authoritative for eligibility, ownership, assessment completion, SAFETY_HOLD routing, lifecycle, idempotency, concurrency, safety boundaries, focus-area evidence computation, grounding-bundle assembly, structured-output validation, and version pinning. The LLM MUST synthesize a personalized bilingual plan from the grounding bundle and MUST NOT determine whether a user is eligible or safe to receive a normal plan. The LLM MUST NOT invent diagnoses, clinical conclusions, medication advice, crisis counselling, or unsupported user facts.
- **FR-006a**: The LLM MUST be accessed only through an app-owned provider port `COACHING_LLM_PORT` (`CoachingLlmPort`) owned by the Coaching module; the AI module MUST supply the adapter and prompt templates. Provider and model selection MUST be configuration-driven; secrets MUST remain server-side. Token, latency, timeout, rate-limit, and cost controls MUST be enforced at the adapter. Automated tests MUST use a deterministic fake adapter (`FakeCoachingLlmAdapter`) and MUST NOT call live paid providers.
- **FR-006b**: The LLM MUST return a strict versioned structured schema (`LlmPlanOutput`) with complete bilingual `{en, ar}` content. The system MUST validate the structured output deterministically before persistence: schema, allowed library identifiers (every goal/action `libraryKey` exists in the pinned library version), limits (focus areas ≤3; action/goal bounds), safety (no clinical/diagnostic/medication/crisis content; concerning-output detection), required sections, assessment traceability, and bilingual completeness (both `en` and `ar` non-empty). Invalid or unsafe output MUST be rejected; no usable plan is persisted (→ `FAILED`).
- **FR-006c**: Generation MUST be asynchronous with **two independent status concepts** persisted on `CoachingPlan`: **GenerationStatus** (`PENDING | GENERATING | READY | FAILED`) for one generation attempt, and **PlanStatus** (`PROPOSED | ACTIVE | COMPLETED`, nullable until generation succeeds) for the plan lifecycle. A plan has no usable lifecycle/content until `generationStatus = READY`. Successful validated generation MUST transition `generationStatus → READY` and `planStatus → PROPOSED` **atomically** (one transaction). Provider/validation failure MUST transition `generationStatus → FAILED` (never a PlanStatus) and persist no usable plan. Execution uses a tracked in-process runner with database-persisted status (no job queue, no Redis). `POST /coaching/plan` MUST idempotently create or return the current plan: it MUST return `202` while `generationStatus` is `PENDING`/`GENERATING`, return the existing resource without invoking the provider when `generationStatus = READY`, and trigger a retry when `generationStatus = FAILED`. `GET /coaching/plan` MUST return `generationStatus` during generation; when `READY` it MUST also return `planStatus` and usable plan content; when `FAILED` it MUST return a safe retryable failure representation. There MUST be no `GET /coaching/plan/:id` (JWT-only ownership).
- **FR-006d**: Because the plan is AI-generated, the system MUST require explicit user acceptance before activation (Constitution IV): `POST /coaching/plan/accept` MUST transition **only** `planStatus: PROPOSED → ACTIVE` (it MUST NOT change `generationStatus`), and MUST be allowed only when `generationStatus = READY` and `planStatus = PROPOSED`. Action updates (`PATCH`) MUST be enabled only when `generationStatus = READY` and `planStatus` is `ACTIVE` or `COMPLETED`.
- **FR-006e**: The system MUST persist generation/audit metadata per attempt in a `CoachingPlanGeneration` row: attempt, provider, model id, prompt/template version, source assessment id/result id/definition version, library version, disclaimer version, generation status, validation outcome (sanitized), retry count, token usage, latency, `started_at`, `deadline_at`, `finished_at`, and a sanitized error code. The parent `CoachingPlan` MUST carry lease metadata (`generationStartedAt`, `generationDeadlineAt`) and a `currentAttemptId` reference to the in-flight attempt. The system MUST NOT persist hidden chain-of-thought and MUST NOT persist raw assessment content or plan copy — only references and operational metadata (Constitution VI).
- **FR-006f**: Async execution MUST be operationally safe without Redis or a job queue and MUST NOT rely on an untracked fire-and-forget Promise after the HTTP response. The `PENDING → GENERATING` transition MUST be an atomic conditional claim (only one worker/request may succeed, so simultaneous retries/claims never start duplicate provider calls). Each in-flight attempt MUST be tracked by a singleton in-process generation runner (registry of attempts with AbortSignals) and bounded by a lease (`generationStartedAt` + `generationDeadlineAt`). Duplicate `POST` requests MUST return the same plan and never duplicate an active provider call. A stale `GENERATING` attempt past `generationDeadlineAt` MUST be recoverable on the next `GET`/`POST` (reclaim to `PENDING`, mark the stale attempt `FAILED` with `TIMEOUT`/`STALE`). Retry MUST operate on the same current plan record (transition `generationStatus: FAILED → PENDING`) and create a new `CoachingPlanGeneration` attempt row. A late result from an expired attempt MUST NOT overwrite a newer successful attempt (the success/failure persist is a conditional update guarded on `currentAttemptId`). Process restart, provider timeout, and simultaneous retries MUST have this explicit recovery behavior. This requires the API process to be a long-running containerized NestJS service; if the deployment cannot keep the process alive between the `202` response and attempt completion, the execution-trigger mechanism is NEEDS CLARIFICATION (A18).
- **FR-007**: The Coaching module MUST own the generation domain rule (eligibility, grounding, validation, persistence, lifecycle); the AI module MUST own the LLM provider adapter and prompt templates and MUST NOT bypass Coaching validation or ownership (Constitution IV; SAD update in §17).
- **FR-008**: The system MUST start generation idempotently on first access by an eligible user; repeated requests, refreshes, reloads, and re-logins MUST return the existing plan and MUST NOT create duplicates or trigger duplicate provider calls; a `generationStatus = FAILED` plan MUST be retried on the same `CoachingPlan` row by transitioning `generationStatus: FAILED → PENDING` and creating a new `CoachingPlanGeneration` attempt (A18). Duplicate `POST` requests while an attempt is active (`PENDING`/`GENERATING`) MUST return the same plan and start no new provider call; while `READY` they MUST return the resource without invoking the provider.
- **FR-009**: The system MUST pin each plan to its source `assessment_id`, assessment `definition_version`, `result_id`, `library_version`, `disclaimer_version`, and `prompt_version` at creation time and MUST NOT silently recompute or overwrite a plan from a changed assessment.
- **FR-010**: The system MUST NOT generate diagnoses, clinical conclusions, medication advice, or unsupported claims. Plan content MUST be grounded by the approved, versioned coaching library and disclaimer and bounded by the deterministic validation.
- **FR-010a**: The CoachingActionLibrary (focus-area reasons, goals, action steps, bilingual) and the CoachingDisclaimer are required implementation inputs and grounding sources. The LLM may synthesize personalized copy, but every goal and action it emits MUST reference an approved `libraryKey` present in the pinned library version; the validator MUST reject unknown/retired identifiers. The system MUST NOT invent, draft, or hard-code clinical, diagnostic, medication, or otherwise unsupported coaching content. If an applicable library entry is missing or unapproved, or the disclaimer is missing, the system MUST fail closed to the `FAILED`/unavailable state rather than emit fabricated copy (Constitution III).

## 8. Safety Impact and Expected Routing

Plan generation invokes an LLM, so the Constitution II AI safety pipeline is **actively exercised** (not vacuous). Safety impact is both **routing/gating** and **content validation**.

- **Pre-generation eligibility + safety gate**: Only `COMPLETED` + scored result + `NORMAL`/`DISTRESS` gating evaluation may enter generation (FR-001). SAFETY_HOLD/HIGH_RISK/CRISIS never enter generation (FR-004). The assessment result bands are coaching labels, NOT safety levels (feature 001 FR-018); plan focus areas are derived from coaching bands and priorities, never from safety levels. The LLM MUST NOT determine whether a user is eligible or safe to receive a normal plan.
- **Grounding and bounded generation**: The LLM is grounded by the approved, versioned library and disclaimer and bounded by the generation instructions (no diagnosis/medication/crisis/clinical content; bilingual structured output; assessment traceability) (Constitution III).
- **Post-generation safety validation**: The deterministic validator performs a safety check on the LLM output (no clinical/diagnostic/medication/crisis content; concerning-output detection). Unsafe output is rejected → `FAILED`; no usable plan is persisted (Constitution II/IV).
- **SAFETY_HOLD**: `OnboardingState = SAFETY_HOLD` MUST block plan access and route to `/safety/hold` (FR-004). The plan API MUST return the safety-hold routing error and start no generation. A pre-existing `PROPOSED` plan MUST NOT be accepted while `SAFETY_HOLD` (FR-027a). Safety handling takes precedence over plan delivery (Constitution II).
- **DISTRESS**: Eligible (completed via the normal path). The generation instructions enforce bounded supportive framing; the plan adds no clinical claims and no crisis counselling, and post-generation validation backstops this.
- **Fail closed**: If eligibility cannot be determined, the result is missing/inconsistent, the grounding is missing/corrupt/unapproved, the provider fails, the output is malformed, validation fails, or concerning output is detected, the system MUST NOT present a plan; it shows the `FAILED`/unavailable state (FR-012, FR-019). It MUST NOT fabricate a plan or a result (Constitution III).
- **No fabrication**: No invented hotline numbers, emergency contacts, professional resources, diagnoses, or clinical claims appear in the plan. The disclaimer directs users to appropriate professional support when a need exceeds coaching scope (Constitution I).
- **Routing reuse**: Routing reuses the authoritative feature-001 mechanism (`next_route`, `post_onboarding_route`); no new safety-routing authority is introduced (A11).

NO raw answers, NO free-text (`goalFreeText` excluded by default pending privacy review), NO safety data, NO conversation history/memory are sent to the provider.

## 10. AI and RAG Behavior

AI-personalized plan generation is a **core capability** of this feature and is governed by the Constitution (Principles II, III, IV, VI, VII + "AI and RAG" standards).

- **Hybrid architecture**: Deterministic rules assemble the grounding bundle and validate the LLM's structured output; the LLM synthesizes a personalized bilingual plan (schema-bound) via the app-owned `COACHING_LLM_PORT` (FR-006/FR-006a/FR-006b). The LLM does not decide eligibility/safety (Constitution II/IV).
- **Grounded and bounded (Constitution III)**: The LLM is grounded by the approved, versioned CoachingActionLibrary and CoachingDisclaimer; prompts enforce scope, safety, structured output, and bilingual parity; the library constrains allowed ids (validator-enforced). No diagnoses, clinical conclusions, medication advice, crisis counselling, or unsupported user facts (FR-010/FR-010a).
- **Structured and validated output (Constitution IV)**: The LLM returns a defined structured DTO (`LlmPlanOutput`); Coaching validates it for schema, safety, ownership, and domain rules before persistence; invalid/unsafe output is rejected and nothing usable is persisted (FR-006b). The AI module owns the provider adapter and prompts; it does not write to business entities directly.
- **Explicit acceptance (Constitution IV)**: AI-generated plans MUST be explicitly accepted by the user before activation (`PROPOSED → ACTIVE`, FR-006d).
- **Bounded context, no memory (Constitution VII)**: Only the minimum context is shared with the provider; no conversation history/memory; no chain-of-thought persisted (FR-006e, §9).
- **No RAG/knowledge retrieval**: Grounding is via the approved versioned library, not vector retrieval; there is no Qdrant, no embeddings, no RAG pipeline.
- **No AI-coach chat / sessions / streaming**: The LLM is used for one-shot grounded plan synthesis only.

## 12. Failure, Fallback, Retry, and Recovery

- **Loading/generation state**: While `generationStatus` is `PENDING`/`GENERATING`, the dashboard shows a loading/progress state and polls `GET /coaching/plan` (FR-019).
- **Empty/unavailable state**: If the user is eligible but generation cannot produce a plan (missing/inconsistent result, unsupported band/version, missing/corrupt/unapproved grounding, provider failure, malformed/empty output, validation failure, or concerning output), `generationStatus` transitions to `FAILED` (`planStatus` is not set) and the dashboard shows "unavailable" with a retry; no fabricated plan (FR-012, FR-019).
- **Error state**: Subsystem failure (database) shows an error state with retry; the rest of the app remains usable (FR-041).
- **Expired session**: Re-authentication returns the user to `/dashboard` (their `post_onboarding_route`) with the existing plan and progress intact (feature 001 FR-035 precedent).
- **Retry of generation**: A `POST` while `generationStatus = FAILED` (or a reclaim of a stale `GENERATING` attempt) transitions `generationStatus: FAILED → PENDING` on the **same current plan record** and creates a **new** `CoachingPlanGeneration` attempt row (no duplicate plan, no duplicate row); if a usable plan already exists (`READY`), it is returned without invoking the provider (FR-008, A18). Provider timeout/retry is configuration-driven (FR-006a); a provider timeout transitions the current attempt `generationStatus → FAILED` (reclaimable).
- **Stale/restart recovery**: A `GENERATING` attempt past `generationDeadlineAt` (including one orphaned by a process restart) is reclaimed on the next `GET`/`POST` (stale attempt `FAILED` with `TIMEOUT`/`STALE`, `generationStatus → PENDING`); no manual intervention is required (A18, FR-006f).
- **Late-result safety**: A provider result that arrives after its lease expired (or after a newer attempt was claimed) is discarded — it cannot overwrite a newer successful attempt because the persist is guarded on `currentAttemptId` (A18, FR-006f).
- **Retry of progress update**: A retried update is idempotent; setting an action to its current status is a no-op success (FR-030). Optimistic concurrency reconciles stale local state on conflict (the client refreshes its plan view).
- **Concurrent updates**: Conditional updates prevent lost updates; the final state is consistent (FR-033, AC-X5).
- **Provider failure**: Provider failure, malformed/empty output, validation failure, or concerning output → `generationStatus = FAILED`; persist no usable plan; `GET /coaching/plan` returns the safe retryable failure representation; retry on the same row via a new attempt (FR-006c/FR-006f/FR-012). The LLM provider is invoked only through `COACHING_LLM_PORT`; tests use a deterministic fake (FR-006a).

## 16. Resolved Clarifications and Launch Gates

All material product decisions required for `/speckit.plan` are resolved:

- **Generation model**: Hybrid deterministic + LLM; AI-personalized plan generation is a core capability. Coaching owns the generation domain rule; the AI module owns the provider adapter + prompt templates via `COACHING_LLM_PORT` (A2, A13, FR-006/FR-006a/FR-007). Requires an SAD clarification/ADR (see §17).
- **Activation**: Explicit accept-then-activate (Constitution IV), allowed only when `generationStatus = READY` and `planStatus = PROPOSED`: `POST /coaching/plan/accept` transitions **only** `planStatus: PROPOSED → ACTIVE`; `PATCH` only when `generationStatus = READY` and `planStatus` is `ACTIVE`/`COMPLETED` (A4, FR-006d, FR-027a/FR-028).
- **Generation lifecycle (two independent statuses)**: Async start + poll, no new infrastructure. **GenerationStatus** (`PENDING → GENERATING → READY`, or `→ FAILED`) is independent of **PlanStatus** (`PROPOSED | ACTIVE | COMPLETED`); a plan has no usable lifecycle/content until `generationStatus = READY`, which atomically sets `planStatus = PROPOSED`. `FAILED` is a GenerationStatus, never a PlanStatus. Idempotent start (no duplicate plans or provider calls); `FAILED` retry on the same row via a new `CoachingPlanGeneration` attempt (A14, A18, FR-006c/FR-006f/FR-008).
- **Async execution safety (lease + reclaim; no fire-and-forget)**: The `PENDING → GENERATING` transition is an atomic conditional claim; a tracked in-process runner (registry + AbortSignals) bounds each attempt with a lease (`generationStartedAt`/`generationDeadlineAt`); duplicate `POST` never duplicates an active provider call; stale `GENERATING` (incl. process restart) is reclaimed after the deadline; retry creates a new attempt on the same row; late results from expired attempts cannot overwrite a newer success (guarded on `currentAttemptId`). Requires a long-running containerized NestJS process; if not, the execution trigger is NEEDS CLARIFICATION (A18, FR-006f, §15).
- **LLM scope**: Full plan synthesis, grounded + validated; library grounds + constrains allowed ids (not a pick-list); no raw answers/free-text/safety to the LLM (A6/A7/A10/A17, FR-006b/FR-010a).
- **Eligibility**: `COMPLETED` + scored result + `NORMAL`/`DISTRESS` gating evaluation; `SAFETY_HOLD` excluded and never enters generation (A1, FR-001/FR-004).
- **Idempotency**: One current plan per user; idempotent generation start with conditional insert + unique constraint (A3, FR-008), mirroring feature 001 FR-015.
- **Lifecycle**: Minimal `PROPOSED → ACTIVE ⇄ COMPLETED` (PlanStatus only, never touching GenerationStatus), auto-driven by action progress after acceptance (all complete → `COMPLETED`; any reopened → `ACTIVE`); no separate "mark plan complete" control and no pause (A4/A5, FR-022a).
- **Focus areas**: Up to three, prioritized by selected priorities → `support_domain` → lowest bands (A6, FR-014).
- **Action content**: The approved, versioned, bilingual CoachingActionLibrary grounds + constrains the LLM output; no invented clinical/unsupported content; missing/unapproved content fails closed (A7, FR-010a).
- **Schedule**: Ordered sequence with optional pacing label; no calendar dates (A8).
- **Retake safety**: Source-pinned, immutable history; retake triggers a new generation; regeneration user-initiated (A9, FR-009/FR-011).
- **Data exposure**: Derived plan + source ids only; no raw assessment/safety data in responses or to the provider (A10/A17, FR-017).
- **Routing**: Reuses feature-001 `next_route`/`post_onboarding_route`; no new authority (A11, FR-003/FR-005).
- **Concurrency**: Conditional updates / optimistic concurrency; transactional creation (A12, FR-029/FR-033).
- **Generation metadata**: `CoachingPlanGeneration` audit row per attempt (incl. `started_at`/`deadline_at`/`finished_at`); parent plan lease metadata (`generationStartedAt`/`generationDeadlineAt`) + `currentAttemptId`; no chain-of-thought; references + operational metadata only (A15/A18, FR-006e/FR-006f).
- **Safety**: Pre-generation eligibility+safety gate; post-generation safety validation; fail closed throughout (A16, §8).

Launch gates (not planning clarifications):

- The approved bilingual CoachingActionLibrary content (focus-area reasons, goals, and action steps for every focus area the generator can produce) is a **required implementation input**: the feature cannot ship without it. A qualified clinical/safety reviewer MUST approve this library content and the coaching-scope disclaimer text in both languages before public launch. The specification and implementation MUST NOT invent clinical, diagnostic, medication, or otherwise unsupported coaching content as a substitute; missing or unapproved content fails closed to "unavailable" (A7, FR-010a).
- Legal/privacy reviewers MUST confirm the disclaimer and the plan-data retention/deletion behavior align with the approved Consent and Data Retention Policy for every launch jurisdiction.
- No clinical claim, diagnosis, or medication advice may ship in the action library; the library is versioned and independently reversible (Constitution III).
- **Prompt-template review (Constitution III)**: the versioned prompt templates (owned by the AI module, `prompt_version`-pinned) MUST be reviewed for non-clinical, in-scope framing; no instructions that invite diagnosis/medication/crisis content; bilingual parity.
- **Provider data-retention / training policy review (Constitution VI)**: the configured LLM provider's data-retention and training policy MUST be reviewed and documented before production use; bounded context to the provider (assessment evidence codes + minimum profile + library + disclaimer only; no raw answers/free-text/safety).
- **Tests must use deterministic fakes**: automated tests MUST NOT call live paid providers (FR-006a; Constitution VI).
