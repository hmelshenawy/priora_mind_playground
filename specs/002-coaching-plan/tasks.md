## Non-negotiable invariants (apply to every task)

- **Hybrid generation; deterministic rules authoritative**: the LLM synthesizes a personalized bilingual plan from the grounding bundle; deterministic rules are authoritative for eligibility, ownership, assessment completion, SAFETY_HOLD routing, lifecycle, idempotency, concurrency, safety boundaries, focus-area evidence computation, grounding-bundle assembly, structured-output VALIDATION, and version pinning. The LLM **MUST NOT** decide whether a user is eligible or safe to receive a normal plan (Constitution II/IV; FR-006).
- **No invented content**: all plan copy is grounded by `COACHING_LIBRARY_V1` / `COACHING_DISCLAIMER_V1` (sole AUTHORING sources). The library **grounds + constrains allowed ids** — the LLM may synthesize copy but every goal/action MUST reference an approved `libraryKey` present in the pinned library version; the deterministic validator rejects unknown/retired ids. The validator also rejects clinical/diagnostic/medication/crisis/concerning output. The bilingual clinical/legal content of these constants **does NOT yet exist in the repository** (verified 2026-08-01) and MUST be provisioned and approved by qualified clinical/safety + legal/privacy reviewers (T001, blocking) — the implementer (Codex) MUST NOT invent clinical/diagnostic/medication content, and the LLM is instructed not to; validation backstops both (Constitution I/III; FR-010/FR-010a). Until approved content is present, the feature fails closed (`503 PLAN_UNAVAILABLE`).
- **Language-independent generation**: the LLM ALWAYS emits the complete bilingual `{en, ar}` payload; `LanguageCode` is NOT a generation input. The UI locale only selects which persisted bilingual value is displayed and MUST NOT trigger generation or a separate plan/provider call (US4; FR-035).
- **Reference snapshot validation (exact-version lookup + integrity verification)**: before persisting a plan, the backend looks up the `CoachingActionLibrary` row by the **exact required `libraryVersion`** and the `CoachingDisclaimer` row by the **exact `disclaimerVersion`** (no `isActive`/active/approved-flag query), verifies both exist, and verifies each row's stored content matches the authoritative TS constant's (`COACHING_LIBRARY_V1` / `COACHING_DISCLAIMER_V1`) integrity representation; it pins `libraryVersion` + `disclaimerVersion` (+ `promptVersion` on `CoachingPlanGeneration`) on the plan/attempt. If either row is missing, corrupt, or fails integrity verification → `503 PLAN_UNAVAILABLE`, persist nothing, no provider call. **T001 success is the content-approval gate** (no DB approval flag). TS constants = sole authoring source; DB rows = immutable audit/version-pin snapshots (NOT independent content sources).
- **`planVersion` and `isCurrent` are columns on `CoachingPlan`** — NOT a separate `PlanVersion` model/table (research D7; data-model §1).
- **One current plan per user** is DB-enforced by a partial unique index `coaching_plan_current_one_per_user ON "CoachingPlan"("userId") WHERE "isCurrent" = true` (raw SQL in the migration). There are TWO independent status concepts on `CoachingPlan`: `generationStatus` (`PENDING | GENERATING | READY | FAILED`, default `PENDING`) — progress of one generation attempt; and `planStatus` (`PROPOSED | ACTIVE | COMPLETED`, nullable until `READY`) — the plan lifecycle. `FAILED` is a `generationStatus`, NEVER a `planStatus` (no `SUPERSEDED`). A plan has no usable lifecycle/content until `generationStatus = READY` (which atomically sets `planStatus = PROPOSED`). An assessment retake (new `sourceResultId`) triggers a new generation: ONE transaction flips the prior plan `isCurrent=false` (frozen `planStatus`/`generationStatus` untouched) and creates a new `isCurrent=true` plan (`generationStatus = PENDING`, `planStatus = null → … → READY/PROPOSED`) for the new `sourceResultId`; the partial unique index forces this order. Triggered by the user's plan request (user-initiated, satisfying FR-011 — no silent overwrite; history preserved).
- **Generation lifecycle (async, no new infra)**: `POST /coaching/plan` → `202 { plan_id, generationStatus:"PENDING" }`; generation runs in a **tracked in-process runner** (singleton, Coaching-owned; registry of in-flight attempts by `planId`/`currentAttemptId` with `AbortSignal`s — NOT an untracked fire-and-forget Promise) with DB-persisted `generationStatus` (`PENDING → GENERATING → READY` (atomically sets `planStatus = PROPOSED`) or `→ FAILED`); `GET /coaching/plan` returns `202 { plan_id, generationStatus }` while `PENDING`/`GENERATING`, the full plan (with `generationStatus:"READY"` + `planStatus`) when `READY`/`PROPOSED`/`ACTIVE`/`COMPLETED`, and `503 PLAN_UNAVAILABLE { plan_id, generationStatus:"FAILED", retryable:true }` when `FAILED`. No `GET /coaching/plan/:id` (JWT-only ownership). Idempotent start: repeated requests MUST NOT create duplicate plans or duplicate provider calls; `FAILED` re-attempts on the same `CoachingPlan` row (new `CoachingPlanGeneration` attempt) (Constitution IV).
- **Async execution safety (no Redis, no job queue, no fire-and-forget — A18/FR-006f/AC-X13/SC-017)**: atomic generation claim — `PENDING → GENERATING` is a single conditional update (`WHERE generationStatus='PENDING'`) so only one worker/request succeeds (simultaneous retries/claims never start duplicate provider calls); lease metadata `generationStartedAt` + `generationDeadlineAt` on `CoachingPlan` and `deadlineAt` on each `CoachingPlanGeneration` attempt row, plus `currentAttemptId` (loose ref to the in-flight attempt); stale recovery (incl. process restart) — on `GET`/`POST`, if `generationStatus='GENERATING'` AND `now() > generationDeadlineAt`, the stale attempt is marked `FAILED` (`TIMEOUT`/`STALE`) and `generationStatus` returns to `PENDING`; late-result guard — persist is a conditional update guarded on `generationStatus='GENERATING' AND currentAttemptId=:thisAttemptId` (a newer attempt → 0 rows → late result discarded; a late success from an expired attempt can NEVER overwrite a newer successful attempt); provider timeout → `generationStatus='FAILED'` (reclaimable); duplicate `POST` returns the same plan and never duplicates an active provider call. Runtime prerequisite: long-running containerized NestJS process (per plan.md); if serverless/scale-to-zero the execution trigger is NEEDS CLARIFICATION (would need a real queue) — not a blocker under the current deployment.
- **Explicit acceptance (Constitution IV)**: `POST /coaching/plan/accept` is allowed ONLY when `generationStatus = READY` AND `planStatus = PROPOSED`, and transitions ONLY `planStatus: PROPOSED → ACTIVE` (it MUST NOT change `generationStatus`); idempotent no-op for `ACTIVE`/`COMPLETED`. `PATCH /coaching/plan/actions/:action_id` is enabled only when `generationStatus = READY` AND `planStatus ∈ {ACTIVE, COMPLETED}` (else `409 PLAN_NOT_READY` when `generationStatus ≠ READY`, or `409 PLAN_NOT_ACTIVE` when `planStatus = PROPOSED`); accept on `PENDING`/`GENERATING` → `409 PLAN_NOT_READY`; accept on `FAILED` → `409 PLAN_UNAVAILABLE`; accept blocked with `409 SAFETY_HOLD` if the user entered `SAFETY_HOLD` after generation.
- **Provider abstraction**: the LLM is accessed ONLY through an app-owned port `COACHING_LLM_PORT` (`CoachingLlmPort`) owned by Coaching; a new `ai` module supplies the adapter + prompt templates (config-driven provider/model; secrets server-side; token/latency/timeout/rate-limit/cost controls). `FakeCoachingLlmAdapter` (deterministic) for tests; automated tests MUST NOT call live paid providers (FR-006a; Constitution VI).
- **Generation metadata + no chain-of-thought**: each attempt records a `CoachingPlanGeneration` audit row (provider, model id, prompt/template version, source pins, `status` (`generationStatus`), validation outcome, retry count, token usage, latency, `startedAt`/`deadlineAt`/`finishedAt`, sanitized error code). NO chain-of-thought, NO raw assessment content, NO plan copy — references + operational metadata only (FR-006e/FR-006f; Constitution VI). A retry creates a NEW `CoachingPlanGeneration` row (prior rows immutable); `currentAttemptId` on the plan references the in-flight attempt.
- **Bounded context to the provider**: the grounding bundle carries ONLY deterministic evidence (domain codes/bands, `strongestDomain`, `supportDomain`, selected priorities as CODES), the minimum profile fields needed, the pinned library content, the disclaimer, the promptVersion, and the generation instructions. NO raw answers, NO free-text (`goalFreeText` excluded by default pending privacy review), NO safety data, NO conversation history/memory (FR-017; Constitution VI/VII).
- **Backend-authoritative eligibility**: `OnboardingState = COMPLETED` + scored result + `SafetyService.currentLevel ∈ {NORMAL, DISTRESS}`; `SAFETY_HOLD`/`HIGH_RISK`/`CRISIS` excluded with `409` and never enter generation. `userId` always from `req.user.sub`; action_id validated via `plan.userId` join; cross-user → `404` (no leak).
- **No sensitive telemetry**: plan/progress content excluded from logs/analytics/traces/error reports via `toSafeLogContext` (FR-039/SC-010); generation metadata stores no CoT/raw content.
- **300-line rule** (Constitution VIII): split `coaching-plan.service.ts` / `coaching-generation.service.ts` / `coaching-grounding.service.ts` / `coaching-plan-validator.ts` / `coaching-action.service.ts` / `coaching-plan-view.tsx`; migrations, seeds, and `in-memory-prisma.ts` are exempt.
