## Summary

Feature 002 replaces the `/dashboard` future-release placeholder ("Onboarding complete — coaching plan comes in a future release.") with a **personalized, AI-synthesized coaching plan** generated from the persisted feature-001 `AssessmentResult` + profile. The plan is non-clinical, user-owned, persisted, progress-trackable, and fully localized (Arabic/English + RTL/LTR). The architecture is **hybrid deterministic + LLM**: deterministic rules are authoritative for auth, eligibility, ownership, assessment completion, `SAFETY_HOLD` routing, lifecycle, idempotency, concurrency, safety boundaries, focus-area evidence computation, grounding-bundle assembly, and structured-output validation; an LLM **synthesizes** a genuinely personalized bilingual plan (full structured schema) from a deterministic grounding bundle. The LLM MUST NOT decide eligibility/safety and MUST NOT invent diagnoses, clinical, medication, crisis, or unsupported user facts. The backend remains authoritative for eligibility, ownership, and routing; `SAFETY_HOLD` users stay in the existing safety flow and never receive a normal plan.

Technically the feature is a slice of the modular monolith — async generation via a **tracked, lease-bounded, reclaimable in-process runner** + DB-persisted **two-status** state (`generationStatus` + `planStatus`; no job queue, no Redis, no untracked fire-and-forget), NO new infrastructure (no Qdrant, no vectors, no RAG retrieval, no email). It adds two new module surfaces — **Coaching** (CoachingPlan, FocusArea, Goal, ActionStep, CoachingPlanGeneration, plus versioned `CoachingActionLibrary` / `CoachingDisclaimer` reference content) and a new **AI** module (provider adapter + prompt-template management) implementing the `COACHING_LLM_PORT` owned by Coaching — one Prisma migration, one cross-module read export on `AssessmentModule` (`AssessmentResultService.getScoredResult`), one new deletion port (`COACHING_DELETION_PORT` also deleting `CoachingPlanGeneration`) wired into the existing RetentionModule + AccountDeletionService, and a new `coaching` frontend feature area that replaces the dashboard page. Three invariants are load-bearing and non-negotiable throughout the plan:

1. **No invented content.** All plan copy (title, summary, focus-area reasons, goals, action steps, pacing, disclaimer) is grounded in a supplied, approved, versioned, bilingual `CoachingActionLibrary` seed (research D4). The library grounds AND constrains allowed ids — every `libraryKey` referenced by the LLM output MUST exist in the pinned library version (id-constrained, not pick-list). The LLM synthesizes bilingual copy, but a deterministic validator (`coaching-plan-validator.ts`) rejects clinical/diagnostic/medication/crisis content, concerning output, schema violations, unknown library ids, limit breaches, and incomplete bilingual coverage. If generation or validation fails, the system **fails closed** to `FAILED` (503 `PLAN_UNAVAILABLE` on GET) and persists no usable plan (Constitution III; FR-010/FR-010a/FR-012; spec §16 launch gate). The specification and implementation MUST NOT invent clinical, diagnostic, medication, or otherwise unsupported coaching content.
2. **Backend-authoritative eligibility.** Plan access requires `OnboardingState = COMPLETED` + a scored `AssessmentResult` + `SafetyService.currentLevel ∈ {NORMAL, DISTRESS}`. `SAFETY_HOLD` (and HIGH_RISK/CRISIS) are excluded with `409 SAFETY_HOLD` and create no plan — they never enter generation (FR-001/FR-004). Frontend guards (`RequireAuth`, `RequireOnboarding`) remain UX-only (FR-002), as in feature 001.
3. **Explicit user acceptance before activation + two independent async-generation statuses.** Generation tracks **two independent concepts**, modeled as two separate enums (Constitution IV — AI-generated plans must be explicitly accepted before activation):
   - **CoachingGenerationStatus (GenerationStatus)** = `PENDING | GENERATING | READY | FAILED` — the progress of one generation attempt; a column on `CoachingPlan` (default `PENDING`) and on each `CoachingPlanGeneration` attempt row.
   - **CoachingPlanStatus (PlanStatus)** = `PROPOSED | ACTIVE | COMPLETED` — the plan's lifecycle; a NULLABLE column on `CoachingPlan` (`null` until generation succeeds).
   - A plan has no usable lifecycle/content until `generationStatus = READY`. Successful validated generation transitions `generationStatus → READY` and `planStatus → PROPOSED` **atomically** (one transaction). Explicit acceptance transitions ONLY `planStatus: PROPOSED → ACTIVE` (via `POST /coaching/plan/accept`; allowed only when `generationStatus = READY` and `planStatus = PROPOSED`); it never touches `generationStatus`. Action completion transitions ONLY `planStatus: ACTIVE ⇄ COMPLETED`. Provider/validation failure transitions `generationStatus → FAILED` (`FAILED` is a GenerationStatus, NEVER a PlanStatus); `planStatus` stays `null`. Retry changes `generationStatus: FAILED → PENDING` on the **same current plan record** + a NEW `CoachingPlanGeneration` attempt row. A UI locale change transitions neither status and never invokes generation. Generation is asynchronous: `POST /coaching/plan → 202 {plan_id, generationStatus}`; the frontend polls `GET /coaching/plan`, which returns `generationStatus` during generation, `planStatus` + usable content when `READY`, and a safe retryable failure representation when `FAILED`. No `GET /coaching/plan/:id` (JWT-only ownership).
   - **Async execution is TRACKED, not fire-and-forget**: the `PENDING → GENERATING` transition is an atomic conditional claim (`WHERE generationStatus='PENDING'`; only one worker/request succeeds → simultaneous retries never start duplicate provider calls); a singleton in-process generation runner (Coaching-owned) holds a registry of in-flight attempts by `planId`/`currentAttemptId` with AbortSignals; each attempt is lease-bounded (`generationStartedAt` + `generationDeadlineAt`); a stale `GENERATING` attempt past `generationDeadlineAt` (incl. process restart) is reclaimed on the next `GET`/`POST` (`generationStatus → PENDING`, stale attempt `FAILED` `TIMEOUT`/`STALE`); a late result from an expired attempt cannot overwrite a newer successful attempt (the persist is a conditional update guarded on `generationStatus='GENERATING' AND currentAttemptId=:thisAttemptId`). Requires a long-running containerized NestJS process (the deployment per plan.md); if serverless/scale-to-zero → the execution trigger would be NEEDS CLARIFICATION (would need a real queue) — NOT a blocker under the current deployment (A18/FR-006f).

The provider boundary is a dedicated port: `COACHING_LLM_PORT` (Symbol token) + `CoachingLlmPort { generatePlan(bundle): Promise<LlmPlanResult> }` is OWNED BY Coaching (declared at `coaching/ports/coaching-llm.port.ts`); the new `ai` module implements `CoachingLlmAdapter` + prompt-template management with config-driven provider/model, server-side secrets, and token/latency/timeout/rate-limit/cost controls. A `FakeCoachingLlmAdapter` (deterministic) is used for tests — automated tests MUST NOT call live paid providers. `CoachingModule` imports the `AI` module; the `AI` module does NOT import Coaching (no circular DI).

Additional mandated behavior: idempotent start (one `CoachingPlan` row per `userId + sourceResultId`, `@@unique([userId, sourceResultId])`; no duplicate plan or provider call) and **one current plan per user** DB-enforced by a partial unique index `coaching_plan_current_one_per_user ON "CoachingPlan"("userId") WHERE "isCurrent" = true` (raw SQL in the migration — Prisma `@@unique` cannot express the `WHERE` filter); the per-result `@@unique` alone does NOT enforce one-current-per-user across different results, so the partial index is the load-bearing guard; source-pinning to `assessment_id` + `definition_version` + `result_id` + `library_version` + `prompt_version` (immutable history, safe retake boundary); **assessment-retake supersede** — when the latest scored result's `resultId` differs from the existing current plan's `sourceResultId`, ONE transaction flips the prior plan `isCurrent=false` (frozen `planStatus`/`generationStatus` untouched) and inserts a new `isCurrent=true` plan (`generationStatus=PENDING`, `planStatus=null` → `PENDING → GENERATING → READY` atomically sets `planStatus=PROPOSED`) for the new `sourceResultId` (the partial unique index `coaching_plan_current_one_per_user ON "CoachingPlan"("userId") WHERE "isCurrent" = true` forces this flip-old-`isCurrent=false`-then-insert-new-`isCurrent=true` order; triggered by the user's plan request — user-initiated, no silent overwrite; historical plans immutable; retake triggers a new generation); automatic `ACTIVE ⇄ COMPLETED` lifecycle derived solely from action progress (now post-acceptance) with **no separate "mark complete" control** (FR-022a); concurrent/idempotent action-progress updates via conditional `updateMany` + optimistic `version`; ownership-safe APIs (userId from JWT, action_id validated via `plan.userId` join, cross-user → 404 with no existence leak); no raw assessment answers/scores/safety in any response (FR-017) and no raw answers/free-text/safety sent to the LLM (`goalFreeText` EXCLUDED by default — flagged as an open privacy decision); plan/progress content excluded from logs/analytics/traces (FR-039); account deletion removes plans + sub-entities including `CoachingPlanGeneration` (FR-040); and first-class Arabic/English (RTL/LTR) + accessibility throughout.

## Technical Context

**Language/Version**: TypeScript 5.x on both backend (NestJS 11) and frontend (Next.js 16). Node.js 20 LTS runtime (matches feature 001).

**Primary Dependencies**:
- Backend: NestJS, Prisma 6 (PostgreSQL), Zod 3 (DTO/input + structured-output validation), `@nestjs/jwt` + Passport (auth, reused), `@nestjs/schedule` (retention cron, reused). **NEW: an AI provider SDK accessed via `COACHING_LLM_PORT` (config-driven; vendor-agnostic via the port — no specific vendor pinned in this plan)**, the new `ai` module implementing `CoachingLlmAdapter`, and prompt-template versioning. AI provider via `COACHING_LLM_PORT` (config-driven); no Qdrant/no vectors/no RAG retrieval (grounding is via the approved versioned library, not retrieval); no email.
- Frontend: Next.js (App Router), React 19, Tailwind CSS 3.4, TanStack Query 5.100, `next-intl` 4.13, React Hook Form (not used by this feature — no forms), Zod (shared mirror). Hand-rolled UI on shadcn CSS tokens (NO shadcn/ui installation — feature 001 convention).
- Shared: `@priora/shared-types` workspace package — add coaching-plan DTOs (including `LlmPlanOutput` schema mirror) for cross-stack type parity.
- Reference content: deterministic bilingual coaching library + disclaimer sourced from the approved-for-planning v1.0 content, stored as versioned reference data (research D4), like `AssessmentDefinition` / `SafetyCopy`. The library grounds AND constrains the LLM's allowed ids.

**Storage**: PostgreSQL (primary relational store, reused). No file/blob storage. No Qdrant, no vectors, no embeddings. NEW: `CoachingPlanGeneration` table for per-attempt generation metadata (auditability).

**Testing**: Vitest (unit + contract via `InMemoryPrisma` + supertest; e2e against an isolated real test DB, 30s timeout) on the backend; Playwright e2e only on the frontend (stubs backend via `page.route`, no shared auth/seed fixtures — feature 001 convention). Deterministic `FakeCoachingLlmAdapter` for tests — **automated tests MUST NOT call live paid providers**. Grounding-bundle assembly, structured-output validation, generation-state machine, lifecycle, and eligibility logic covered by pure-function fixture tests (no DB, no live AI) mirroring `scoring.spec.ts` / `safety-classifier.spec.ts`. Reproducibility REPLACES determinism: LLM output is non-deterministic, so tests use fakes and assert behavior/contract; generation metadata makes real generations auditable.

**Target Platform**: Linux server (containerized NestJS service) behind HTTPS; Next.js rendered for modern evergreen browsers. No native mobile, no offline.

**Project Type**: web-service (modular monolith backend + Next.js frontend), extending the feature-001 stack.

**Performance Goals**: LLM generation latency budget: generation p95 < 20s (async, client polls); deterministic validation < 100ms; `GET /coaching/plan` (`generationStatus=READY`, `planStatus` ∈ `PROPOSED`/`ACTIVE`/`COMPLETED`) < 300ms p95 server-side; `PATCH .../actions/:id` < 200ms p95. Product-internal targets, not public SLAs (matches feature 001).

**Constraints**:
- Non-negotiable: AI via `COACHING_LLM_PORT` only; deterministic validation MUST precede persistence; no invented clinical/unsupported content; fail-closed on generation/validation failure; no sensitive content (plan/progress) in logs/analytics/traces/error reports; no raw assessment answers/safety to the LLM or in API responses; `SAFETY_HOLD` blocks plan access (pre-generation gate); explicit user acceptance before activation (Constitution IV); provider data-retention/training policy reviewed before production (launch gate).
- Async-execution safety (lease-based tracked in-process runner; no Redis, no job queue, no untracked fire-and-forget): the `PENDING → GENERATING` transition is an atomic conditional claim (`WHERE generationStatus='PENDING'`); a singleton Coaching-owned in-process runner holds a registry of in-flight attempts (`planId`/`currentAttemptId`) with AbortSignals (tracked, observable, cancelable — NOT a bare Promise); each attempt is lease-bounded (`generationStartedAt` + `generationDeadlineAt` on `CoachingPlan`; `deadlineAt` on the `CoachingPlanGeneration` attempt row); stale `GENERATING` past the deadline (incl. process restart) is reclaimed on the next `GET`/`POST` (`generationStatus → PENDING`, stale attempt `FAILED` `TIMEOUT`/`STALE`); retry operates on the same plan row (`generationStatus: FAILED → PENDING`) + a NEW attempt row; a late result from an expired attempt is discarded (persist guarded on `generationStatus='GENERATING' AND currentAttemptId=:thisAttemptId`); duplicate `POST` returns the same plan and never duplicates an active provider call. **Runtime prerequisite**: this requires a long-running containerized NestJS API process (the deployment per plan.md); if the deployment is serverless or scales the API to zero between requests, the in-process runner cannot survive and the execution-trigger mechanism is NEEDS CLARIFICATION (it would require a real queue) — NOT a blocker under the current long-running container deployment (A18/FR-006f/§15).
- Reproducibility replaces determinism: LLM output is non-deterministic, so tests use deterministic fakes (`FakeCoachingLlmAdapter`) and assert behavior/contract/reproducibility-of-deterministic-components; `CoachingPlanGeneration` audit metadata makes real generations auditable. Automated tests MUST NOT call live paid providers.
- Bilingual: every user-facing plan string and state exists in AR + EN with equivalent meaning; RTL/LTR tested, not just `dir`; the disclaimer never silently cross-fallbacks (spec §11, feature 001 §12 precedent); the LLM is instructed to produce complete bilingual output and the validator rejects incomplete AR/EN coverage.
- 300-line rule for handwritten source files (Constitution VIII); split coaching services (grounding/validator/generation/action), the AI adapter, and the dashboard view to stay under.
- One entity, one owner module (SAD §5 / ADR-005); cross-module reads go through exported services, never direct table access (research D2). `CoachingPlanGeneration` is owned by Coaching; the AI module owns only the provider adapter + prompts.

**Scale/Scope**: Single-tenant MVP scale (thousands of users). 2 new modules (Coaching + AI) + 1 cross-module read export + 1 deletion port + 1 frontend feature area; **7 Prisma models** (4 user-owned: `CoachingPlan`, `FocusArea`, `Goal`, `ActionStep`; 1 new audit: `CoachingPlanGeneration`; 2 versioned reference: `CoachingActionLibrary`, `CoachingDisclaimer`) + **3 new enums** — `CoachingPlanStatus` with 3 values `PROPOSED|ACTIVE|COMPLETED` (nullable on `CoachingPlan` until `generationStatus=READY`), `CoachingGenerationStatus` with 4 values `PENDING|GENERATING|READY|FAILED` (default `PENDING` on `CoachingPlan` and on each `CoachingPlanGeneration` attempt row), and `ActionStatus`; 1 ordered migration; replaces 1 placeholder page. New `CoachingPlan` columns: `generationStatus` (default `PENDING`), `planStatus` (nullable), lease metadata `generationStartedAt` + `generationDeadlineAt`, and `currentAttemptId` (nullable ref to the in-flight `CoachingPlanGeneration` row). New `CoachingPlanGeneration` column: `deadlineAt` (lease expiry for that attempt). Partial unique index `coaching_plan_current_one_per_user ON "CoachingPlan"("userId") WHERE "isCurrent" = true` (raw SQL — Prisma `@@unique` cannot express the `WHERE` filter). `PlanVersion` (spec §7 Key Entity) is modeled as the `planVersion` + `isCurrent` columns on `CoachingPlan` (research D7), **not** a separate table. No external integration beyond the AI provider. No Qdrant, no payments, no notifications, no async queue, no email.

**Structure Decision**: Web application structure — NestJS modular monolith backend organized by SAD §5 module boundaries (auth, profile, assessment, safety, **new coaching**, **new ai**, platform retention), Next.js App Router frontend organized feature-first per Frontend §4. ## Complexity Tracking

> **Fill ONLY if Constitution Check has violations that must be justified**

Constitution XII simplicity is maintained by the AI-personalization requirement being a core product capability (not gold-plating). Three additions are justified below; async via a **tracked, lease-bounded, reclaimable in-process runner** + DB-persisted two-status state (no job queue, no Redis, no fire-and-forget) keeps XII satisfied.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| New `ai` module + `COACHING_LLM_PORT` provider port | Required by the hybrid deterministic + LLM model: AI/LLM personalization is a core product capability (PRD §8). The port keeps the provider vendor-agnostic and config-driven, isolates secrets/server-side config, and enables a deterministic `FakeCoachingLlmAdapter` so automated tests MUST NOT call live paid providers (Constitution IX + cost discipline). | An inline provider call inside Coaching would violate one-owner-per-entity (Constitution IV/VIII), block vendor-agnostic config, and make tests hit live paid providers. A shared "platform LLM" module would blur Coaching's ownership of the generation domain rule. |
| `CoachingPlanGeneration` table (Coaching-owned) | Required for auditability of non-deterministic LLM output (Constitution IX reproducibility-replaces-determinism): one row per attempt capturing attempt, provider, modelId, promptVersion, sourceAssessmentId, sourceResultId, definitionVersion, libraryVersion, disclaimerVersion, `generationStatus`, validationOutcome, retryCount, tokenUsage, latencyMs, `started_at`/`deadline_at`/`finished_at`, sanitized errorCode. NO CoT, NO raw assessment content, NO plan copy — references + operational only. | Persisting only the final plan would make generations unauditable and non-reproducible (no way to investigate FAILED/rejected outputs or track provider cost/latency). Storing full prompt/response/CoT would violate Constitution VI/VII (no sensitive content, no CoT persisted). |
| Tracked in-process generation runner + lease (atomic claim, stale reclaim, late-result guard) — Coaching-owned singleton, no Redis/job queue | Required for **operational safety** of the async start+poll model without new infrastructure (A18/FR-006f/§15): the atomic `PENDING→GENERATING` conditional claim prevents duplicate concurrent provider calls; the lease (`generationStartedAt`+`generationDeadlineAt`, `currentAttemptId`) bounds each attempt and recovers from process restart / lost workers / long provider calls via lazy reclaim on the next `GET`/`POST`; the `currentAttemptId`-guarded persist discards late results from expired attempts so a newer successful attempt can never be overwritten. The runner is a **tracked** registry of in-flight attempts with AbortSignals (observable/cancelable), not a bare fire-and-forget Promise. This is the simplest design that is actually safe under the long-running containerized NestJS deployment; it adds zero infrastructure. | A bare fire-and-forget Promise after the `202` would be simpler but is unsafe: simultaneous retries could start duplicate paid provider calls, a process restart would orphan in-flight work with no recovery, and a late success could overwrite a newer attempt. A real Redis/job queue would be safer under serverless/scale-to-zero but is out of MVP scope and unneeded under the current long-running container deployment; if the deployment changes to scale-to-zero, the execution trigger becomes NEEDS CLARIFICATION (would need a real queue) — recorded as a deployment prerequisite, not a planning blocker. |
